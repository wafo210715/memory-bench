# graphmemix-p1-3conv 作废声明

作废时间：2026-09-12 23:30 GMT+8
处置：本 run 的 evidence 与 answers 全部作废，不得用于任何结论或对比。
接替 run：`graphmemix-p1-3conv-v2`（版本边界，不混用修改前后的结果）。

## 作废原因

启动后约 5 分钟，答题 endpoint 大面积返回 429 限流。被测 server 的内部 LLM 调用
（`servers/graphmemix/server.py` 的 `_llm_json`）当时把限流错误与 JSON 格式错误混在同一个
except 分支里处理：三次快速重试、无退避，耗尽后返回 None，调用方降级为"全部候选零分"。

后果不是该题失败，而是产出了一条看不出问题的证据：节点验证与关系验证都没跑成，
节点效用完全由检索分决定，可信图一条边都没有，森林必然退化成独立点集。
这会把"机制根本没被激活"误记成"森林在 LoCoMo 上退化"——正是本轮实验要测的那个结论被静默污染。

已产出 108 行 evidence（36 题真实计算 + 72 次缓存命中），其中 45 行带森林退化标记，
无法区分哪些是真实退化、哪些是限流降级，因此整体作废而不是挑出受污染的部分。

## 为什么算结构性错误而不是可重试的运行故障

按 implement-check-run 阶段 3 的失败处理梯度：同配置重试解决不了它——重跑还会在限流时
走同一条降级路径。修的是代码，所以必须另开版本边界。

## 修复内容（已进入 v2）

1. 限流与服务端错误（429 / 5xx / 连接超时）单独识别，走与 `bench/llm.py:34` 同一套长退避
   序列 [5,10,20,30,45,60,60,60]，原样重发不回灌格式校正；退避耗尽抛错，让该题明确失败，
   不再降级产出证据。
2. 格式类错误保留上游的回灌校正协议，重试三次，与限流退避分开计额度。
3. 两次验证任一失败，逐题在 native_notes 打 NODE_VERIFIER_FAILED / ECV_FAILED，
   出分时可统计；stats 增加 llm_transient_retries 与两个失败计数。

修复后 smoke 重跑 8/8 全过。

## 补记：v2 第一次启动同样作废（23:33-23:36）

原因与代码无关，是启动前的环境失误：v1 跑完 Phase A 后留下了 `locomo_full` 快照，
而 v2 是新 run-id、进度文件为空。runner 在"有未完成 conv 且快照存在"时的行为是
先 restore 再从头补灌（bench/runner.py:224-231），于是同一批 1297 条记忆被灌了两遍，
`memories.jsonl` 出现 2594 行、唯一 id 仅 1297。已产出的 15 行证据一并作废。

处置：删除 graphmemix 的 state 与快照、删除 v2 run 目录后从零重灌，重灌后确认 1297 条无重复。

经验（已同步到 servers/graphmemix/REPRO-NOTES.md）：同一条臂换 run-id 重跑前，
必须先清掉它的 `.state/<arm>` 与 `__snapshots__/<arm>`，否则快照与进度文件不同步会导致重复灌入。

## 补记：对同期其他 run 的干扰与恢复

清理时把 `rag_baseline` 的 `locomo_full` 快照一并改名，而用户同期运行的 memharness run
（PID 59184，arms 含 rag_baseline）依赖该快照。发现后立即改回原名并核验快照完整
