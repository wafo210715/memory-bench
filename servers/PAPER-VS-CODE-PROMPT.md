# 复用 Prompt：单系统 paper ↔ code 对照

> 2026-09-06 从 letta 那一轮跑通后沉淀。用法：把下面 `====` 之间的内容整段粘给新会话，
> 把 `<SYS>` 全部替换成目标系统目录名（`mem0` / `graphiti` / `memos` / `atommem` / …）。
> 样板产出见 `servers/letta/paper-vs-code.md`。

====

在 `memory-bench` 仓库里为 `<SYS>` 产出一份 paper ↔ code 对照，写入
`servers/<SYS>/paper-vs-code.md`。

## 0. 动手前必须先问（AskUserQuestion）

检查 `servers/<SYS>/server.py` 是否存在、`<SYS>` 是否注册在仓库根 `servers.yaml` 的 `servers:` 下。

两者成立 = 这个系统 memory-bench 自己复现过，除了「论文」和「上游代码」之外还有第三个来源：
本仓库的臂 / adapter 实测行为。

此时必须用 AskUserQuestion 问用户：要两列（paper / code）还是三列（paper / 上游 code /
memory-bench 臂）。不要替用户决定，也不要默认两列就开工。

截至 2026-09-06 复现过的系统：`amem` `graphiti` `mandol` `mem0` `memos`。
`amem` 和 `mandol` 另有 `ARCHITECTURE.md`，那就是本仓库臂的实测版文档，做三列时以它为第三列的事实源。

其它需要抉择的地方同样用 AskUserQuestion，不要闷头选一个：
要不要写 benchmark 一节、发现证据与既有文档冲突时怎么处理、某条差异重要度拿不准时。

## 1. 事实来源（按优先级，不得跳级）

| 级别 | 来源 | 说明 |
|---|---|---|
| 1 | `servers/<SYS>/verification.md` | 唯一事实源，逐条复核结论 + 证据行号 |
| 2 | `servers/flowgen/specs/<SYS>-paper.json` / `-code.json` | 阶段归属、`prim`、`cite` |
| 3 | `wafo-base/literature/papers/*.txt` | 仅在 verification 未覆盖时读原文 |
| 4 | 上游代码仓库 | 只读核实。只用 `git show <ref>:<path>`，不 checkout、不改仓库 |
| 5 | `servers/<SYS>/ARCHITECTURE.md` + `server.py` | 只在做三列时用，代表本仓库臂的实测行为 |

禁止把 `paper-architecture.md` / `code-architecture.md` 的表述当事实——它们是被复核的对象，
已知含 ✗ 和 ◐。

## 2. 输出结构

```text
frontmatter（title / date / tags: memory-bench, paper-vs-code, <SYS>）
# 标题
> [!note] 口径      —— 各来源的确切版本 + 事实源 + 时代差 + 空格含义
## A 段 · 形成期（query-independent）    表格：阶段 | Paper | Code〔| 本仓库臂〕
## B 段 · 动员期（query-conditioned）    表格：阶段 | Paper | Code〔| 本仓库臂〕
（如有两侧都空的阶段）> [!tip] 成因说明
## 差异清单                              表格：全部差异，一行一条，带重要度与类型
## 重点差异详述                          只展开重要度「高」的，每条 3–5 行
## 附：推导（可选，0-3 条）
```

十四个阶段固定按此顺序，一个不少、不改名：

```text
A1 intake   A2 distill   A3 admit   A4 index   A5 commit   A6 internalize
B1 cue   B2 recall   B3 expand   B4 appraise   B5 select   B6 deliver   B7 generate   B8 loop
```

## 3. 差异清单怎么写

列出发现的全部差异，不做数量裁剪。宁可多列，也不要因为「不够重要」而丢掉——
读的人可以跳过低重要度的，但看不到没写的。

清单是一张表，一行一条：

| # | 阶段 | 差异 | 类型 | 重要度 |
|---|---|---|---|---|

类型三选一（这三类性质完全不同，别混着说）：

- 能力损失 —— 论文有、代码没有或退化了
- 设计演进 —— 两边都有，但机制换了
- 纯加法 —— 代码有、论文没有
- 文档脱节 —— 代码里的文档/注释当下就与实现矛盾（不是新旧问题）

重要度按判据定，不按感觉：

| 重要度 | 判据 |
|---|---|
| 高 | 改变了「这个系统能做什么」。某能力一侧有一侧没有；或文档承诺了实现里不存在的东西，会误导读者 |
| 中 | 能力边界没变，但机制换了，或默认值、阈值不同。影响复现和调参，不影响对系统的定性判断 |
| 低 | 实现细节。换库、改命名、多一层封装。记下来备查，不必展开 |

`重点差异详述` 一节只展开重要度为「高」的，每条 3–5 行带证据。中和低的留在清单里即可。
若「高」的条目超过五条，用 AskUserQuestion 问用户要不要全展开。

## 4. 硬规则

1. 空就真的空。该阶段不存在时，单元格留空白，不写「空——因为…」。理由压到表下的 callout。
   这张表的价值就是一眼看出哪些格子亮着，解释性文字会毁掉这个。

2. 区分「空」和「默认死」。空 = 不存在；默认死 = 代码完整、逻辑齐全，但默认配置不可达
   （被显式摘除、开关未开）。默认死不是坏了，也不是缺 API key——必须找到那行把它关掉的代码
   （集合减法、deprecation 列表、环境变量判断）才能这么标。

3. stage 做行，paper/code 做列。14 列在 Markdown 里不可读。

4. 表格外的字要短。详述每条 3–5 行，带证据行号，不要展开成小作文。
   但短不等于碎：精简时删的是冗余信息，不是句子的语法。详见下一条。

5. 用自然语言写，代码术语降级为括号注解。这是最容易犯、后果最大的一条。

   证据文件里全是代码标识符和工程术语，写的时候很容易直接把这些词拼起来、丢掉语法。
   正确做法：句子主干说人话，讲清楚「这一步在干什么、由什么决定」；函数名、常量名、
   精确数值、章节号放进括号做注解。类比：解释一个函数时先用人话说它干什么，
   最后才括号补上它的真名。

   检验方法：把格子念出来，是不是一句能听懂的话。不是就重写。

   为什么这条特别重要：这是一张跨系统对比表。标签拼接的格子没法跨行比较，因为每个系统
   的标签都不一样。写成「触发方式看的是上下文占用率」，才能和另一个系统的「触发方式看的
   是消息条数」放在一起读。先说机制属于哪一类，再给具体值。

   附带好处：标签拼接能掩盖「其实没搞清因果」，写成完整句子会把这个漏洞暴露出来。

   letta 的 A3 三个版本对比：

   ```text
   差 —— 标签拼接（精简时把语法删掉了，只留术语）
     压力警告 "e.g. 70%" → 冲刷 "e.g. 100%、驱逐 e.g. 50%"（都是举例值）；外加 LLM 自编辑工作上下文

   好 —— 自然语言主干，数值降级为注解
     压缩由上下文占用率触发：超过阈值先警告，到上限就冲刷队列、驱逐一半
     （论文写的是 e.g. 70% / 100% / 50%，都是举例值不是硬编码）。
     另有一步 LLM 自己改写工作上下文，论文把抽取和冲突处理合并成了一次调用。
   ```

   差的那版问题在于：读的人得先认识「冲刷」「自编辑工作上下文」这些术语才能还原意思，
   而且看不出这三件事之间的先后和因果。好的那版先给出机制类型（由占用率触发），
   再补具体数字，因果链也顺出来了。

6. 全文禁止用 `**` 加粗。用户要复制粘贴这些内容，星号会跟着跑出去。需要强调时用
   「」引号、独立成行，或靠表格与小标题的结构。行内代码 `` ` `` 可以用。

7. 先声明时代差。在口径 note 里写明 paper 年份和 code 快照日期。相隔越久，越应默认
   「差异 = 演进」而不是「论文说谎」；只有文档与实现当下互相矛盾（如 docstring 承诺了已删的
   能力）才判为「文档脱节」。

8. benchmark 单独处理，且不跨年代并列。2023–2024 年的论文多用自建/改造评测（MSC、DMR、
   nested KV…），2026 年的普遍用 LOCOMO、LongMemEval。不同年代的数字不能放进同一张对比表。
   若用户要 benchmark，单开一节写：任务名 / 题型 / 指标 / 数字 / 基线模型，并标注年份。

9. 注意因果链，别把结果当独立观察。例：A4（建索引）空 → B2（召回）只能弱 → B4/B5 必然空。
   这是一条链，不是四个并列事实。清单里可以分行列，但要在「差异」列写明它依赖哪一条。

## 5. 判断阶段归属时的常见坑

- 数据库索引不是 A4 index。SQL 的 B-tree 索引是建表时一次性创建的静态 schema，属于 A5 载体的
  属性；A4 说的是对每条记忆都要跑一次的可寻址性构建（算 embedding、建倒排、连边、建 ANN）。
  判据：问「这一步是不是每来一条记忆都要跑一次？」
- 实验装置不是运行时机制。论文里为跑评测做的离线预处理（如预计算语料 embedding）经常填满
  某个阶段，但它不是系统运行时会做的事。`verification.md` 通常已经这样标注了，照抄它的判断。
- 同一机制跨阶段复用是合法的（写入期查重的向量检索 @A3 对查询期召回 @B2），不是矛盾。
  见 `flowgen/MODEL.md` §1 三层结构与 `flowgen/README.md` 的合法多义白名单。
