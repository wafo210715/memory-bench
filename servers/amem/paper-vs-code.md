# A-MEM Paper ↔ Code 对照

> [!note] 口径
> paper = arXiv:2502.12110v11（Xu et al. 2025，首次提交 2025-02）
> 上游 = `agiresearch/A-mem` @ `ceffb86`（2025-12-12），论文作者本人的实现，相隔约十个月
> fixed 臂 = memory-bench 自建修复臂（`servers/amem/fixed.py`，`MEMBENCH_AMEM_MODE=fixed`），
> 与上游是同一份代码打补丁，无时代差
> 事实依据以同目录 `verification.md` 为准；本轮另抽查上游与 fixed 臂关键证据行逐条复核。
> 空格 = 该阶段在这一侧不存在。「零调用点」= 函数实现完整但全仓库无人调用，
> 比「默认死」更彻底：不是被开关关掉，是从未接线。

## A 段 · 形成期（query-independent）

| 阶段 | Paper | 上游 `agiresearch/A-mem` | memory-bench fixed 臂 |
|---|---|---|---|
| A1 intake | 每次 agent 与环境交互留下一条记忆，只带原文和时间戳（§3.1） | 同样一条一条收，但记忆对象建出来时三个语义字段全落在默认空值上 | 同上游；说话人与日期由评测脚本先拼进原文，属系统边界外 |
| A2 distill | 一次 LLM 把原文炼成关键词、标签和一句话摘要，各自至少三个（Eq.2，提示词 Ps1） | 零调用点：函数连提示词原文都写全了，全仓库却没有一处调用它（`:159` 是它自己的定义），语义字段永远停在默认值 | 把这次调用接回去，解析失败才退回默认值（实测 852 条全部成功） |
| A3 admit | 先按富文本向量找出最相似的一批老记忆，再逐条让 LLM 改写它们的摘要与标签（Eq.4-5、Eq.7） | 找邻居传的是原文而不是富文本向量；改写时把检索名次当成记忆列表的下标，实际改的是最早存进来的前五条，不是找到的邻居 | 邻居列表带上真实编号，按编号定位改写，并记下被改过的条目留待重新索引；查询侧仍传原文，这一点与论文不符 |
| A4 index | 记忆向量由原文与关键词、标签、摘要拼在一起编码（Eq.3）；另一次 LLM 依据邻居决定连哪些边（Eq.6，提示词 Ps2） | 只编码原文，语义字段进元数据不参与向量化；连边时 LLM 只看得到「第 i 条」这样的序号，连出来的边指向不存在的编号。另有每满百次演化重建一次全库索引，论文没有这一步 | 改编富文本；连边先过滤到真实存在的编号；被改写的邻居在每个 session 末逐条重算向量 |
| A5 commit | 记忆集合里每条含七个字段，改写后的记忆直接替换原件（Eq.1、§3.3）。全文没说怎么落盘 | 只活在进程内存里，不落盘；向量库另存一份索引 | 内存加按 scope 分开的向量库；另把内存序列化成 json，供跨进程恢复 |
| A6 internalize | | | |

## 三点最大区别

### 1. 论文的语义抽取从未接通，而文档还在承诺它 ——【能力损失 + 文档脱节】

论文 Eq.2 要求每条记忆先由 LLM 抽出关键词、标签和一句话摘要。上游把这个函数完整写了出来，
连 Ps1 提示词原文都在，却没有任何一处调用它：全仓库搜 `analyze_content` 只命中它自己的定义
（`memory_system.py:159`），`add_note` 直接拿原文构造记忆对象（`:238`）。
失败时的回退值恰好等于字段默认值（`:231` 对 `:68-72`），从外部完全看不出破绽，
而上游 README 至今写着 "Creates contextual descriptions and tags"（README:44,161）。
这一格塌了会顺着往下塌：语义字段恒为默认 → 即使按 Eq.3 编富文本也只能编出空值 →
A3 改写的摘要与标签对检索永远不生效。

### 2. 三处指针全指错，病根是同一个 ——【能力损失，实现缺陷不是演进】

邻居检索返回的是枚举序号而不是记忆的真实编号（`:307-308`），于是同一个病根长出三处故障：
连边把 "0"、"1" 这类序号写进 links（`:682`）；改写邻居时 `indices[i]` 恒等于 `i`，
改的是最早插入的前五条（`:687-716`）；检索期沿边扩展算出来的邻居，
又被 `return memories[:k]` 一条不剩地截掉（`:585`），实测邻居标记恒为 0。
判缺陷而不判演进的依据：若是主动砍掉这条能力，`:554-583` 那段扩展逻辑会一并删除，
而它完整保留着 —— 算了又扔。

### 3. 修复臂补通了论文机制，却丢掉了上游唯一的生命周期步骤 ——【回归】

fixed 臂逐条修回了上面两条，但覆盖 `add_note` 之后只留下计数器自增（`fixed.py:385-387`），
上游那句「每满一百次演化就重建全库索引」的判断（`memory_system.py:260-263`）没有跟过来；
`fixed.py:389` 定义的重建函数全仓库无人调用，server 层的对应补丁只挂在 native 分支
（`server.py:230` 位于 `else:` 内）。
这是 `verification.md` 全篇唯一一条判为不实的断言（A21）：
`ARCHITECTURE.md` ⑤ 把一个只属于 native 臂的行为写进了 fixed 臂的主流程。
