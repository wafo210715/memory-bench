> 开跑前要先知道什么。论文↔上游代码↔本臂的三列对照在同目录 `paper-vs-code.md`，机制拆解在
> `methodology-flow.md`，逐条核验证据在 `verification.md`，契约在 `docs/interface-spec.md`；
> 本文件只记这条臂的复现决策与验证证据。

## 0. 这条臂在测什么

GraphMemix 把"该给 agent 看哪些记忆"形式化成一个查询到来后才求解的组合优化问题。它与其他记忆臂的
结构性差别集中在三点：

1. 写入期几乎不做加工——只把每条记忆编码成向量，外加一张与查询无关的关系图（结构关系边 + 语义
   互近邻边）。写入期不调生成式模型。
2. 查询期用两次并行的模型调用分别回答两个不同的问题：这条候选本身有多大用（节点验证），
   以及在某条已选锚点已知的前提下这条候选还新增了多少信息（关系验证，并从六个角色里选一个贴上：
   新事实 / 澄清 / 佐证 / 冗余 / 冲突 / 无关）。第二个问题是其他臂都不问的。
3. 最终交付的是一片森林而不是一个列表：给几条是算出来的（变基数精确求解），顺序也有语义
   （锚点在前，经可信关系恢复的上下文在后）。

所以跨臂比较时，本臂相对 rag_baseline 这类纯向量臂的差异，应当主要归因于上面第 2、3 条，
而不是检索强度——两者的召回入口都是同一个 embedding-3 余弦检索。

## 1. 口径决策表

| # | 分叉 | 判法 | 理由 |
|---|---|---|---|
| 1 | 核心算法自己写还是引上游 | 引上游原版 | 候选图发现、1-swap + Kruskal、穷举变基数三段是论文一号贡献，上游自包含可 import，重写只会引入不可控偏差 |
| 2 | 胶水层（写入编码 / 多视角检索 / 证据序列化）怎么办 | 按论文补齐 | 上游这三段在 `ConcreteMemixMethod`，硬依赖仓库里没有、README 也没给下载方式的私有包 `vendor/memix-core`（concrete_memix.py:48-52），只能按论文 §3.3 Eq.3 与 Appendix A.5 实现 |
| 3 | 编码器用哪个 | embedding-3 | 与 mem0 / graphiti / mandol / rag_baseline / atommem 同口径，排除"嵌入强度"这个跨臂变量。代价是节点效用 sigmoid 的输入尺度会漂，由 `prize_probes` 观测 |
| 4 | 证据预算 K 取论文的 10 还是契约的 top_k | 取 top_k | K 在 Eq.1/Eq.11 里的语义就是"交给 reader 的证据条数上界"，与 top_k 同义。固定 10 而其他臂给 20，比的是证据预算不是选证据能力 |
| 5 | K=20 时 Eq.13 的 2^20 穷举怎么办 | 按连通分量分解后逐块调上游 `exact_subset` | 目标函数在正收益边不相连的节点组之间可加，分解是数学等价而非近似。实测每块通常不超过 8 个节点 |
| 6 | schema 关系用哪几种 | 只有 `consecutive_turn` | 上游 `explicit_edges` 只认两个字段，LoCoMo 经 loader 交来的 turn 没有配对的 native round 字段。与论文 Appendix A.1 对 H2HMem 的处理同型，不是实现缺失 |
| 7 | 多视角检索在纯文本上怎么办 | 退化为单视角，显式声明 | loader 层已丢弃图像描述，Eq.3 的 max-pool 退化成恒等。GraphMemix 的多模态部分因此未被本臂测到 |
| 8 | 节点效用系数用论文的还是上游拟合的 | 论文 Eq.14 展开 | 上游 `shared_dev.json` 那组是用 gold 证据标签在四个多模态数据集的 fold-0 上拟合的，我们没有对应 dev fold，嵌入也换了，不可移植。两组系数逐项差 2-8%（a 2.6% / b 7.7% / c 1.9%），同输入下 p_i 的差异更小 |
| 9 | 两次 listwise 调用并行还是顺序 | 真并行 | 论文 §4.1/§4.4.4 两处无条件断言并行；上游因 query-image caption 只在节点阶段生成而被迫顺序。LoCoMo 无图，该依赖不存在 |
| 10 | envelope 排序按 score 降序还是森林序 | 森林序 | Appendix A.5 的顺序本身是机制的一部分。契约 §4 的降序是给无原生顺序的系统设的默认值，graphiti 的混合类型排序已有先例 |
| 11 | retrieve 调 LLM 这件事怎么归类 | active retrieval 面，成本表单列 | 两次调用都读候选记忆正文，与 atommem 的"只读 query"不同类，也不能并进零 LLM 纯检索栏 |
| 12 | retrieve 非幂等怎么办 | 加查询级缓存 | 见下一节 |

### 决策 12 的完整论证（本轮唯一一处为契约而加、论文里不存在的机制）

契约 §1 要求 `retrieve` 幂等。但本臂的 retrieve 路径调 LLM，服务端 batching 的浮点非确定性会让
节点验证分微动，在变基数精修的临界值附近（效用约等于 0.12）让节点一进一出。2026-09-12 的
smoke 第 5 步（restore 后同 query 结果一致）实测报 FAIL，就是这个原因：同一 query 两次返回
4 条和 5 条。

做法是把结果按 `(query, query_mode, top_k, scope_id, 库内容 sha256)` 缓存在进程内。库变了指纹就变，
自然不命中；`reset()` 之后再 `restore()` 回相同内容时指纹变回旧值、命中缓存，这正是契约要的幂等。
修复后 smoke 在空库与 422 条大库两种条件下各跑一次，都是 8/8。

代价必须写明：`bench/runner.py:240` 的 `n=3` 是同一个 server 进程内重复调 `retrieve`，缓存会把本臂
检索侧的方差归零。这与 mem0 / graphiti / rag_baseline 等确定性检索臂的行为一致（它们三个 rep 的
evidence 本来就逐字相同），n=3 测的是答题 LLM 的方差。要单独测 GraphMemix 自己的检索侧波动，
用 `MEMBENCH_GRAPHMEMIX_CACHE=off` 跑一轮对照，不混进主跑。

附带收益：主跑时 rep2/rep3 命中缓存，内部 LLM 调用量从 3 倍降回 1 倍。

### 第二层 对抗审查

2026-09-12 完成，报告在同目录 `review-2026-09-12.md`。

模型偏离要先说清楚：仓库纪律规定实现审查由 `claude-fable-5-1` 做，该模型当天连续两次
返回渠道 503（No available accounts）且零产出，第三次改由 `claude-opus-4-6` 执行。
审查人与实现人因此属于同一模型家族的不同代，对抗性弱于原定配置，读结论时要考虑这一点。

结果：CRITICAL 0 条、MAJOR 0 条、MINOR 5 条，判定“可以开跑”。五条 MINOR 已当场全部修复：

| # | 问题 | 处置 |
|---|---|---|
| F1 | API 调用成功但 JSON 解析失败时 `llm_calls` 双计 | 加 `counted` 标志，同一次调用只计一次 |
| F2 | `reset()` 返回的 `cleared` 缺 `memories` / `sessions` 计数（契约 §5 模板有） | 清空前先读一次计数再返回 |
| F3 | 口径 8 声称系数差“不到 4%”，b 系数实际差 7.7% | 改成逐项的 2-8%，并说明输出差异更小 |
| F4 | 关系图惰性构建写在缓存判定之前，命中时也会重建 | 移到缓存未命中分支内 |
| F5 | 节点验证解析保留了 0 分条目，上游只收正分 | 加 `value > 0` 过滤，与上游对齐 |

修复后重跑 smoke，仍为 8/8（见 §2 第一层）。

### 第三层 口径核查

- thinking：内部 LLM 走 `extra_body` 注入，三态映射与 mem0 / atommem 对齐，默认 `low`
  （thinking enabled + reasoning_effort=low）。非 low 档把 max_tokens 提到 128k，防思考吃光额度。
- 同口径对比：本臂属 active retrieval 面，已在 `docs/interface-spec.md` §7 的检索面分栏单列，
  不进零 LLM 纯检索主表。
- 公平性偏离项：编码器、K 的取值、效用系数、多视角退化、schema 关系缺项、查询缓存六项全部
  登记在 interface-spec §7 的逐系统配置清单。
- 配置漂移留痕：本臂首次入矩阵，无历史 run 可比。
- 判分器口径：沿用全局 F1 + LLM-judge 双轨，cat5 只走 judge，本臂无特殊处理。
- 可区分阈值：105 题约 6.7pt、558 题约 3.1pt，低于阈值不下结论。n≥3 仍必要（答题侧）。

## 4. 开跑前须知

### 4.1 效用探针基线（换编码器后的尺度漂移观测起点）

`stats().prize_probes` 记录节点效用分布。LoCoMo conv0 上的基线：最小 0.09、中位 0.14-0.16、
最大 0.30。

这组数字要和上游拟合记录对照着看：`configs/release/calibration/shared_dev.json` 记录的正例占比是
0.135、平均概率 0.1348，也就是说上游在自己的四个数据集上，节点效用的期望水平也在 0.13 附近。
本臂换了编码器之后中位数落在同一量级，说明 Eq.14 的固定超参在 embedding-3 的余弦尺度上没有失效。
这是开跑前最需要先确认的一件事，因为变基数精修的保留判据就是"效用高于 0.12"——效用整体塌到
0.05 会让本臂只返回个位数证据，整体升到 0.5 则精修形同虚设。

### 4.2 森林在 LoCoMo 上高度退化，这是本轮最重要的观测

同一批探针里：

- 节点验证平均只给 48 条候选中的 2.75 条打了非零分；
- 关系验证返回 65 行、丢弃 0 行，六角色分布是无关 51、澄清 7、冗余 7，新事实和佐证都是 0；
- 经过角色过滤后剩下的可信边平均每题只有 1.2-1.75 条；
- 最终森林的连通分量数是 18.9，也就是 20 个节点里将近 19 个是孤立点。

丢弃 0 行这个数字排除了实现层面的嫌疑：模型返回的行全部通过了 id 与锚点合法性校验，边是被
模型判成"无关"而消失的，不是被解析吃掉的。所以这是 LoCoMo 这个任务的性质决定的：
本臂能用的结构关系只有"相邻对话轮"，而 LoCoMo 的问题大多答案落在单条 turn 里，相邻轮次是闲聊
延续，确实没有增量价值。真正可能提供跨 session 增量的语义近邻边，按论文 §3.4 的设计不参与关系验证。

后果要写进任何用到本臂的结论里：在 LoCoMo 上，森林优化实质退化成"按节点效用取 top-K"，
GraphMemix 相对纯向量检索的机制增量基本没有被激活。逐题上报的 `FOREST_DEGENERATE` 标记
可以在出分后统计这个比例，不要事后凭印象说"图记忆没用"。

按论文复现的原则，这里不做任何"改进"（例如把语义边也放进关系验证）。要验证这个判断，
正确做法是换一个证据天然跨记录分布的 benchmark，而不是改机制去迁就 LoCoMo。

### 4.3 成本与时长（小样本实测，未做全量外推）

按 10 题实测线性推算，LoCoMo 全量 1,986 题一轮的内部 LLM 消耗约 13.6M token，
是本矩阵里构建期最省、检索期最贵的一条臂（构建期零生成式调用）。开缓存时 n=3 不会让这个数字翻倍。
retrieve 并发 16 下，单轮检索阶段预计 15-25 分钟，不含答题与判分。

## 5. 门禁判定

三层全绿，可以开跑：机器门禁 8/8 与 pytest 无新增红；对抗审查 CRITICAL 0 / MAJOR 0，
五条 MINOR 已当场修完并重跑门禁；口径核查逐项过完。正式跑分前还要做的只剩冻结代码指纹
与写 run manifest（包括本文 §1 的十二条口径与 §4.2 的退化观测）。

审查报告同时给出两个独立结论，值得单独记一笔：口径 5 的连通分量分解确实与全局穷举等价（目标
函数可加，tie-break 差异不改变目标值）；口径 12 的缓存不存在“库内容不同但指纹相同”
或“同指纹下返回过期结果”的路径。
