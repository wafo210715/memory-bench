### F1 · MINOR · llm_calls 在 JSON 解析失败时可能双计

位置：server.py:262 与 server.py:265

`_llm_json` 函数中，如果 API 调用成功（`client.chat.completions.create` 返回）但随后 `json.loads` 抛出 `JSONDecodeError`，执行流会先经过 :262 的 `_stats.llm_calls += 1`，再因异常跳到 except 块的 :265 `_stats.llm_calls += 1`，导致同一次 API 调用被计数两次。

影响：仅影响 stats 报告的 llm_calls 统计，不影响实际行为或计费 token 计数。当前探针数据显示 0 次 JSON 解析失败（`llm_parse_failures: 0`），因此该分支尚未被触发。

修复建议：将 :262 的 `_stats.llm_calls += 1` 移到 `return` 语句之后不可达的位置是不行的；正确做法是把 `json.loads` 放在 try 块外面（先赋值 raw_content，try 只包 API 调用，外面再 json.loads），或者在 except 块里检查 response 是否已获取再决定是否计数。

### F3 · MINOR · 口径 8 声称系数差异"<4%"，b 系数实际差 8.4%

位置：server.py 文件头口径 8 注释；REPRO-NOTES.md §1 第 8 行

口径 8 写"与上游拟合值相差 <4%"。三组系数的实际百分比差异：
- a：|4.16 − 4.054| / 4.054 = 2.6%
- b：|0.208 − 0.2254| / 0.2254 = 7.7%（以上游为基准）或 |0.208 − 0.2254| / 0.208 = 8.4%（以论文为基准）

修复建议：将"<4%"改为"各系数差异 2–8%，输出 p_i 差异更小（sigmoid 压缩）"。

### F4 · MINOR · retrieve 路径在缓存命中前也会触发 _adjacency() 的惰性构建

位置：server.py:736

`retrieve` 函数在缓存查询之前调用了 `adjacency = _adjacency()`（:736），而缓存检查在 :738-745。如果关系图尚未构建（首次 retrieve 或 restore 后），即使最终缓存命中也会先完成整个关系图构建。

影响：仅影响 restore 后首次 retrieve 的延迟（需要重建关系图），不影响正确性。由于关系图构建结果有 `_adj_cache` 缓存，后续调用不会重复构建。实测场景下，restore 后的首次 retrieve 通常不会命中查询缓存（因为 restore 后 `_corpus_sha` 被重置，需要重新计算指纹），所以这条路径在实际运行中基本不构成额外开销。

修复建议：将 `adjacency = _adjacency()` 移到缓存未命中分支内部。非阻塞。

### F5 · MINOR · verifier 解析包含 score=0 的条目，与上游过滤行为微异

位置：server.py:569-576（`_node_verifier` 返回值构造）

server.py 的 `_node_verifier` 返回所有解析成功的条目（`max(0.0, min(5.0, ...))`），包括 score 为 0 的。上游 score_graphmemix_verifier.py:346 显式过滤 `if value > 0`，只保留正分条目。

修复建议：在 `out[mid] = ...` 后加 `if out[mid] <= 0: del out[mid]`，或改为先赋临时变量再判断。非阻塞。

不存在会让 runner 静默出错的路径。smoke 8/8 通过的结果与本次代码审查一致。

### 问题 3 · 口径 5 的数学等价性

结论：等价性成立。

论证如下。

Eq.13 的目标函数：
```
J(S, F) = Σ_{i∈S} (p_i − node_cost − root_cost) + Σ_{e∈F} B_e
```
其中 `B_e = root_cost − λ·c_e`（Eq.12），只有 `B_e > 0` 的边才可能被 Kruskal 选入森林。

_exact_prune（server.py:627-664）先用 benefit > 0 判据过滤边（:629-633），再用 union-find 连通这些正收益边的端点（:642-644），将节点集合分成若干块（:645-647）。块与块之间没有任何正收益边——因为正收益边已被穷举，不在同一块说明不存在。

对于没有正收益边相连的两组节点，J 在它们之间没有耦合项（无 B_e 跨组），因此全局优化等价于对各组独立优化：max J(S) = Σ_c max J(S∩C_c)。

关键验证点：_exact_prune 的 benefit 判据与 exact_subset 内部的 benefit 判据（evaluate_graphmemix_exact_pruning.py:73-76）逐字一致——都是 `root_cost - edge_weight * -math.log(max(similarity, 1e-6)) > 0`，使用同样的 root_cost=0.12 和 edge_weight=0.1。不存在 _exact_prune 漏掉了 exact_subset 内部会使用的正收益边、或反之的情况。

Tie-break 差异不产生实质影响。exact_subset 的 tie-break 规则（evaluate_graphmemix_exact_pruning.py:103-107）是 `(value, -len(members), tuple(-i for i in members))`，其中 `i` 是节点在 ordered_ids 中的索引。分组后各块独立调用 exact_subset，块内索引（members 在该块的 ordered_ids 中的位置）可能与全局索引不同，导致目标值相等时选择不同的子集。但目标值不变，即最优解的质量不受影响。

溢出防护：单个分量超过 EXACT_PRUNE_MAX_NODES=18 时按效用降序截断（:652-654），native_notes 标 EXACT_PRUNE_TRUNCATED。该情形在 LoCoMo 上未观测到（探针 exact_prune_truncated = 0）。截断使该分量的搜索空间不完整，退化为近似而非精确，但由于是防御分支且未触发，不影响当前跑分的等价性保证。

### 问题 4 · 口径 12 的缓存安全性

结论：安全。不存在"库内容不同但指纹相同"或"同一指纹下返回过期结果"的路径。

缓存 key 构造（server.py:738-740）：
```
sha256(f"{query}|{query_mode}|{top_k}|{scope_id}|{_corpus_fingerprint()}")
```

_corpus_fingerprint()（:305-313）对 _MEM_FILE 内容算 SHA256 并截取前 16 个十六进制字符（64 位）。

失效时机逐条核验：

1. add_conversation（:680-703）：写入新记录后调用 _mark_relations_dirty()（:702），该函数将 _corpus_sha 置 None（:321）。下次 _corpus_fingerprint() 从新文件内容重算。新指纹与旧缓存条目的指纹不同，不会命中旧条目。
2. reset()（:833-840）：_state.hard_reset_dir() 清空状态目录（所有文件删除），然后 _mark_relations_dirty() 置 _corpus_sha = None。后续空库的 retrieve 会在 :720-722 的空库检查处提前返回，不进入缓存逻辑。
3. restore(tag)（:896-904）：_state.restore(tag) 用快照目录覆写状态目录，然后 _corpus_sha = None（:900）。下次 _corpus_fingerprint() 从恢复后的文件内容重算。若恢复到之前查询过的状态，指纹相同、缓存命中——这正是幂等性的保证。
4. 查询缓存不清的设计（:317-318 注释）：reset 后再 restore 回相同内容，指纹变回旧值，命中旧缓存。这是契约要求的行为，不是缺陷。

"库内容不同但指纹相同"的可能性：需要两份不同的 memories.jsonl 产出相同的 SHA256 前 64 位。SHA256 的 64 位截断提供约 2^32 = 43 亿个不同库状态的抗碰撞能力。对于基准测试工具，这远超实际需求。

向量文件（_VEC_FILE）不参与指纹计算：向量始终从记忆内容派生（add_conversation 中同步写入 :693-699），restore 恢复整个目录（包含 .npy），因此向量与记忆内容保持一致。不存在"记忆未变但向量变了"的路径。

缓存容量限制（_CACHE_LIMIT=4096）：溢出时 FIFO 淘汰最老条目（:825-826）。LoCoMo 全量约 2000 个唯一查询，n=3 重复时后两次命中缓存，总缓存条目不超过 2000。即使溢出，被淘汰条目在下次查询时重算，得到的可能是不同结果（LLM 非确定性），但这就是关缓存时的原始行为——不构成数据污染。

### 问题 5 · 复现忠实度

结论：未发现在论文没授权的地方"改进"或"退化"机制的情况。

逐条核验：

- ECV 只判 schema 边（语义边不参与）：_ecv 函数中 eligible 计算（:596-600）遍历 adjacency 中 `rel == "explicit"` 的边，语义边（rel == "semantic"）被排除。这与论文 §3.4 Eq.7 的 `(a,i) ∈ E_schema` 限定一致，也与上游 score_graphmemix_ecv.py:203-216 的 explicit_relations_from_store（只收 explicit_relations 非空行）一致。grep 确认 _ecv 函数体内不含 "semantic" 字符串。
- 锚点选择按冻结检索序：anchors = candidates[:ANCHOR_COUNT]（:783），其中 candidates 由 candidate_pool 返回，保持检索序。ANCHOR_COUNT=10 取自上游 configs/release/graphmemix.json:33 的 anchor_count。这与上游 anchor_mode=atomic（score_graphmemix_ecv.py:263,424-425）的行为一致。
- 证据序列化顺序：继承 solve_forest_greedy 内置的排序（上游 probe_graphmemix_pcsf.py:225-242），_exact_prune 后通过 `[mid for mid in ordered if mid in kept]` 保持原序（:662）。这与上游生产行为一致：prune 后只做 mask 过滤、不重排（paper-vs-code 差异 11）。论文 Appendix A.5 定义的序列化应作用于最终选中的森林，但代码和论文在此处存在已知差异，本臂跟随代码而非论文。

本臂为契约添加的唯一机制是查询级缓存（口径 12），论文中不存在。该机制是为满足 interface-spec §1 的 retrieve 幂等性要求而引入，代价（检索侧方差归零）已在 server.py 注释、REPRO-NOTES.md §1 和 interface-spec §7 三处显式声明，且提供了 MEMBENCH_GRAPHMEMIX_CACHE=off 的对照手段。不属于对论文机制的"改进"。

### 问题 6 · 探针数据的解读

结论：森林高度退化（连通分量 18.9/20、ECV 78% 判 irrelevant）是 LoCoMo 任务性质决定的真实退化，不是实现层面的缺陷。

判据：

1. 解析完整性排除了实现层嫌疑。ECV 返回 65 行、丢弃 0 行（_probe["ecv_rows_dropped"] = 0）。65 行全部通过了 id 合法性、anchor 合法性、eligible 约束三重校验（server.py:608-617）。边不是被解析吃掉的，而是被模型判成 irrelevant（51/65 = 78%）或 redundant（7/65）后被角色过滤排除的（POSITIVE_ROLES 只含 new_fact / clarification / corroboration）。
2. 角色分布合理。new_fact=0、corroboration=0、clarification=7——本臂在 LoCoMo 上能用的唯一 schema 关系是 consecutive_turn（同 session 内相邻轮次），而 LoCoMo 的问题大多答案落在单条 turn 中，相邻轮次是闲聊延续，确实缺乏跨记录增量信息。clarification 出现 7 次说明模型偶尔认为相邻轮对锚点有补充价值，这比全部 irrelevant 更可信。
3. 碎片率与论文原生基准可比。论文 Table 6 报告四个多模态基准在 K=10、ECV 配置下的平均分量数为 8.53-9.75，即 85%-97.5% 的节点是孤立点。本臂在 K=20 下观测到 94.5%（18.9/20），落在论文自身报告的区间正中。高碎片化是 ECV"宁缺毋滥"的验证机制的设计输出，不是异常。
4. 变基数精修的行为可解释。节点效用中位数 0.14-0.16，PRUNING_ROOT_COST=0.12。按 Eq.12，孤立节点保留条件是 p_i > root_cost = 0.12。绝大多数候选的效用刚好在阈值之上，因此平均只删 0.1/20 个节点，与观测一致。
5. 验证方式。若要区分"LoCoMo 性质导致"与"实现缺陷"，正确做法是在一个关系类型丰富、跨记录证据密集的数据集上做对照，看碎片率是否下降。按论文 Table 6，ATM-Bench（schema 边均值 6.23）的碎片率比 H2HMem（schema 边均值 6.75 但类型更少）低，说明丰富的 schema 类型确实能降低碎片化。LoCoMo 只有一种 schema 类型，碎片率高于论文任何一个原生基准是合理预期。
