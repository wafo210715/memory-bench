## 0. 这条臂在测什么

MemHarness 的论文标题就是它的一号机制：记忆是重构的，不是复现的。检索命中之后、真正拿去用之前，
插入一次独立的模型调用，把历史经验改写成贴合当前情境的指引；如果判定这条经验在当前情境下
根本不适用，就输出一个空标记把它整条丢掉。所以这条臂与其他记忆臂的结构性差别只有两处：

1. 每条记忆都带着「当初是在什么状态下学到的」这份来源观察，重构时拿它和当前情境并排比较；
2. 取回的东西不会原样进入证据，要么被改写，要么被拒。

其余部分（向量召回、相似度去重、按会话蒸馏）都是常规做法。因此跨臂比较时，本臂相对
mem0 这类事实抽取臂的差异，应当主要归因于上面两条，而不是检索强度。

论文原生跑的是具身与网购 agent 环境（ALFWorld、WebShop）并配 GRPO 训练；本臂把它迁到
LoCoMo 长对话问答的静态强制调用设定，训练层不复现。迁移带来的全部代价在 §1 逐条留痕。

| 8 | 写入与检索去重 | 两条都按上游基础默认 0.85 开启 | 上游两个 benchmark 的配置不一致：ALFWorld 的脚本显式关掉，WebShop 未覆盖即维持开启。两者对 LoCoMo 都没有强对应关系，取基础默认（代表上游的通用选择）而非某个 benchmark 的特例 |
| 9 | 采样温度与思考深度 | 温度 0，思考档位沿用全臂默认（低档），偏离上游重构层的温度 1 加随机采样 | interface-spec §7 的硬要求。这项偏离会降低重构输出的多样性，但不消除其非确定性，实测见 §4.2 |
| 10 | 答案生成 | 不在本臂内做，retrieve 只回证据 | 契约要求；也与上游一致（上游的动作生成是第二次策略前向，属 agent 侧不属记忆系统） |
| 11 | 每段会话蒸馏几条 | 8 条，偏离上游实际的 1 条 | 上游送进提示词的数量是 `max(1, min(num_memories_per_trajectory=1, max_pairs_per_episode=8))` = 1（`experience_summarizer.py:1202-1203`，`ppo_trainer.yaml:416/423`，两个训练脚本均未覆盖）；8 只是硬上限。上游一条轨迹 = 一个单一任务，一条经验够用；LoCoMo 一个 session 是 15-35 轮多话题对话，取 1 会让全库只剩百条量级。设 `MAX_PAIRS=1` 可回上游口径。此条由对抗审查指出（原本误标为“上游默认”） |
| 12 | 写入去重的比较范围 | 限定在同一 scope 内 | 上游的最近邻探测跑在单 task 存储上（`milvus_store.py:193-197` 用 `task_name` 限定），本仓库的等价物是 scope。若跨 scope 比，一条与别的对话相似的记忆会在写入时被丢弃，而检索又按 scope 过滤，导致该对话永远拿不到它（证据静默缺失且无告警）。由对抗审查发现，已修并加回归验证 |
| 13 | 重构调用失败怎么算 | 抛异常中断，不降级为“模型判拒” | 上游的重构跑在本地 vLLM 的 `generate_sequences` 里，不存在远端调用失败这一类；它的拒绝判定处理的是输出格式非法。把两者合并会让一段限流窗口静默地变成“这批题没证据”，事后无法逐题定位。现与其他臂行为对齐（崩掉靠 resume 续跑）。同上，由对抗审查发现 |

### 决策 4 的完整论证（本轮唯一一处改动了上游提示词的地方）

上游的蒸馏提示词要求模型产出「可复用的建议：下次该做什么、该检查什么」，并明令
「不要写成复述」。这套措辞是为 ALFWorld 和 WebShop 写的——那里的经验天然是动作策略。

搬到长对话问答上，这套措辞没有对应物。照搬会让模型产出「回答关于搬家的问题时，注意核对时间线」
这类空洞原则，把「六月搬去 Oakland」这个事实本身丢掉。那样跑出来的低分归因于提示词域不匹配，
不是归因于重构机制，结论没有价值。

裁决：保留两段式结构与 JSON 形状不变，只把域描述换成对话会话，并允许内容字段承载自足的事实陈述
（明确要求保留说话人名与日期）。论文对经验的定义是「自然语言经验」，由任务域决定形态，
并没有规定必须是动作建议；换域就必须换域描述。

代价说清楚：这样一来，本臂与 mem0 那种事实抽取臂的差异就收敛到了「重构层 + 来源观察」这两项上。
这恰好让跨臂对比更受控，但也意味着本臂不再能回答「经验式记忆 vs 事实式记忆哪个更适合问答」
这个问题——要回答它，得用 `MEMBENCH_MEMHARNESS_DISTILL_STYLE=agentic` 跑上游原版提示词做对照，
该开关已实现但本轮未跑。

## 2. 门禁状态（implement-check-run 三层）

### 第一层 机器门禁

| 检查 | 结果 |
|---|---|
| `python main.py smoke memharness` | 6-7/8，不固定。四次实测：三次 7/8（失败项为步骤 8）、一次 6/8（步骤 5 与 8）。两个失败项同根，归因见下 |
| `pytest` | 全绿，无新增红（慢臂按设计跳过） |
| env / 解释器 | `main.py arms` 显示 memharness env 齐；主 venv 即可，无需独立 venv |
| stdio 通道 | 全部日志走 stderr，未出现 JSONRPC 解析错误 |
| 端到端（真实 LoCoMo） | 6/6 全过，见 §3 |

先说为什么不固定：本臂的 envelope 是重构出来的文本，模型生成在温度 0 下仍非确定，
而 smoke 的步骤 5 比较的是「恢复前后两次检索返回的记忆编号集合是否相同」。
当库里只有 1 条记忆时这个集合稳定；一旦有 2 条以上，重构层接受哪几条就会变，断言随之浮动。
这不是快照功能坏了：§3 在英文真实数据上用关掉重构层的纯检索面验过，恢复前后编号集合 9 对 9 完全一致。
即存储层正确，浮动来自存储层之上的重构层。

smoke 步骤 8 的归因，三条证据构成完整链条，不是推测：

1. 泄漏是假阳性。步骤 8 用中文关键词「冰岛/极光」判断 A 侧结果里有没有混进 B 的内容。
   本臂的重构是以当前题面为条件生成的，题面里的「冰岛」会自然出现在改写后的文案里，
   于是关键词命中，但那条记忆本身仍是 A 的。三次采样中两次触发这种命中，
   而跨 scope 的记忆编号在六次采样里恒为 0 条。
2. 关掉重构层复跑，泄漏立刻归零（`MEMBENCH_MEMHARNESS_ADAPTOR=off` 时「A 内 B 泄漏 0 条」），
   直接证明泄漏来自文案改写而非数据串。
3. B 侧自检失败的根因是输出语言被改写。上游的蒸馏与重构提示词全是英文，论文还把
   「严格英文输出」写进格式奖励，并给重构层专门加了对中日韩等非拉丁字符扣分的项——
   英文输出是上游的设计意图，不是缺陷。实测中文样本上蒸馏层三次里两次输出中文、一次输出英文；
   重构层三次全部改写成英文（返回内容正确，是 Iceland / aurora / guesthouse，只是中文关键词匹配不上）。

> [!warning] 豁免声明
> 步骤 5 与 8 都按 MAJOR 处理并豁免，不按 CRITICAL。理由不是「解释得通」，而是有正面证据：
> §3 在目标语料域（英文 LoCoMo）上，用记忆编号前缀这一硬判据重做了同等强度的隔离检查
> （A 侧跨 scope 0 条、B 侧自检通过），并在关掉重构层的纯检索面上重做了快照恢复检查
> （9 对 9 一致，非空集）。两项在目标域上都有更硬的替代证据。
> 启动正式 run 时须把本节连同 §4.2 的非确定性与 §4.3 的中文语料警告一并写进 run manifest。
> 附带说明：不修改 smoke 断言。smoke 是全臂共用门禁，为单臂改判定标准会削弱其他臂的回归保护。
> 后人跑出 6/8 不是新问题，先对照本节再判。

### 第二层 对抗审查

2026-09-12 派 fable 5.1 子会话做只读对抗审查，产出 2 CRITICAL / 4 MAJOR / 10 MINOR。
它同时复核了两段照抄的提示词（与上游配置逐字一致）、拒绝判定逻辑（与上游逐分支等价）、
检索链路（与上游的先扩后收一致），以及 smoke 步骤 8 的豁免理由是否成立。

两条 CRITICAL 均已修复并实证：

| # | 问题 | 修法与验证 |
|---|---|---|
| C1 | 写入去重拿全库向量做比较，而检索按 scope 过滤；另一个对话里相似度达阀的记忆会在写入时被静默丢弃，该对话之后永远拿不到它（破坏 spec §2/§3 的对话间隔离契约） | 去重候选池改为只取同 scope 的行。新增回归验证：把已灌过的会话原样灌进另一个 scope，修复前增量必为 0，修复后实测 16→20 且新 scope 能检索到内容 |
| C2 | 重构调用失败被折算成“模型判拒”，逐题不可区分；评测循环对 retrieve 不重试，一段限流窗口会让整轮 run 惄惄变成空证据 | 改为抛出专用异常中断，与其他臂行为对齐；同时每次 retrieve 逐题上报 `ACCEPTED=k; REJECTED=m`，事后可逐题归因证据为何变少 |

MAJOR 处理：

- M1 蒸馏连续 3 次解析失败会让整段会话静默消失——已改为按契约 §6 返回 `PARTIAL_INGEST` 且接收轮数计 0，
  与“模型合法地判定无高价值内容”区分开（后者报 `NO_MEMORIES`）；同时补上模型返回 JSON 数组时的分支。
- M2 每段会话 8 条被我误标为“上游默认”——已核实并登记为决策 11（偶数第 11 条），同步写进 spec §7。
- M3 会话数统计在从快照恢复起跑的进程里恒为 0（mem0 已踩过同一坑）——已改为从磁盘重算。
- M4 未检查输出是否被截断，截断后的空输出会与“判定不适用”不可区分——已记录结束原因并新增截断计数；
  思考档位高于低档时把生成额度从上游的 256 提到 8192（同 graphiti/amem 的防线先例）。

同时修掉的 MINOR：模块级客户端单例（全量 run 约十万次重构调用，避免反复建连接池）、
探针不再把“候选池为空”计入均值（原本会系统性拉低均值、干扰尺度漂移观测，修后均值从 0.54 升到 0.59-0.61）、
记录与向量改为先写临时文件再连续替换（两文件行序错位会让检索静默归因到错误记忆）、
加载时断言两者行数一致、全拒判定改用本次计数而非累计计数器、
验证脚本改用独立状态目录并在结束时清理（否则正式 ingest 后误跑会清掉当前状态，并把验证快照留给正式 run）。

修复后按 implement-check-run §2.4 重走了第一层机器门禁（不是只重跑失败项），过程中门禁抳出了两个新问题：

- 我引入的回归：向量保存的临时文件名不以 `.npy` 结尾时，numpy 会自动追加后缀，使重命名找不到源文件。
  同时暴露出记录与向量分两次写会留下行序错位的脏状态，改成先写两份临时文件再连续替换。
- C2 修复的次生问题：把调用失败改成抛异常之后，一次瞬时限流就会中断整个 run。
  本臂每题要发 top_k 次重构调用，是其他臂的十几到二十倍，这个风险在长跑里是必然而非偶然。
  已在每次模型调用上加指数退避（3 次重试，2/4/8 秒加抖动），只处理限流、服务端 5xx 与连接失败，
  耗尽后仍然上抛——退避是抗抱瞬时波动，不是把失败藏起来。重试次数计入 `stats().retry_count`。

审查指出但未改的（记录备查）：重构提示词整体截断而非上游的逐字段截断（LoCoMo 最长 session 6708 字符，不会触发）；
retrieve 会回写取用计数，严格讲不是无副作用调用（结果不受影响，在此声明）；ingest 桶只计嵌入成本、
蒸馏计入内部模型桶（与 atommem 同、与 mem0 不同，跨臂看 ingest 列时需两者相加）。

### 第三层 口径核查

- 思考深度：三态映射与 mem0/atommem 对齐（低档 = 开思考并把推理力度压到 low）。
  端到端 80 次调用中解析失败与接口失败均为 0，无思考吃满额度的迹象。
- 同口径对比：本臂 retrieve 会读记忆内容并逐条调 LLM，属主动检索，与 intent 的二级精读同类。
  它的检索延迟与内部模型成本不可与零 LLM 检索面（mock / rag_baseline / mem0 / graphiti / mandol / memos）
  并列，也不同于 atommem 那种「只读题面不读记忆」的查询理解调用。已在 interface-spec §7 的三栏分类中登记为第四类。
- 公平性偏离项：嵌入模型、温度、重构宽度、蒸馏提示词域迁移四项已登记进 spec §7。
- 统一配置：top_k=20、温度 0 未动；三轮取平均属跑分参数，由 runner 控制。
- 配置漂移：本臂为新增，无历史 run 可比，无漂移。

## 3. 端到端验证（真实 benchmark 数据，走完整 MCP 工具链）

脚本留在仓库里可重跑（用独立状态目录，跑完自清，不会碰正式 run 的状态）：
`.venv/bin/python servers/memharness/e2e_verify.py`。
2026-09-12 修完审查问题后实测 7/7 全过，conv-26 前 2 个 session（scope A）+ conv-30 第 1 个 session（scope B），
共 35 turns，top_k=20：

- 落库：16 条记忆 / 3 个 session（每 session 蒸馏出 3-8 条，未触发写入去重）。
- 写入去重不跨对话（C1 回归）：把已灌过的会话原样灌进第三个 scope，记忆数 16→20、新 scope 能检索到内容。
  修复前这一步的增量必为 0，是判定 C1 是否真修好的唯一硬证据。
- 契约合规：4 道真实题，字段齐全、文案不超 600 字符、条数不超 top_k。
- scope 隔离：A 侧返回的记忆编号 100% 带 A 的前缀，跨 scope 0 条；B 侧返回内容正确且无 A 的编号。
  这条用编号前缀判定，不依赖任何关键词匹配，比 smoke 的判据更硬。
- 无空召回：4 题全部有证据返回（这条在重构层全拒时会失败，属概率性断言，见 §4.2）。
- 快照恢复：在关掉重构层的纯检索面上验证，重置后 0 条、恢复后命中编号集合完全一致（8 对 8，非空集比空集）。
  必须在纯检索面上验，否则重构层的非确定性会把存储层的正确性掩盖掉（第一版验证脚本就是在这里误判为失败的）。
- 逐题上报生效：每题的 `native_notes` 现在会写明这次重构了几条、接受几条、拒绝几条，
  例如 `RECONSTRUCTED=8; ACCEPTED=1; REJECTED=7`。
- 机制生效证据：蒸馏出的内容确实保留了说话人名与消解后的日期，例如
  `Jon lost his banking job on 2023-01-19 and subsequently planned to open his own dance studio`；
  重构后的文案是以题面为条件的指引式陈述，不是原文摘录。

## 4. 开跑前须知

### 4.1 阈值探针基线（嵌入模型换代后的尺度漂移观测起点）

| 探针 | 评估次数 | 触发次数 | 最高相似度 | 平均相似度 |
|---|---|---|---|---|
| 写入去重 0.85 | 17 | 0 | 0.6826 | 0.5884 |
| 检索去重 0.85 | 52 | 0 | 0.6826 | 0.6111 |

（这是修掉审查 MINOR 之后的口径：候选池为空的那一次不再计入均值。修之前均值分别是 0.5432 / 0.5375，
被无可比对象的零值系统性拉低，会让人低估相似度分布的真实位置。）

两条线一次都没触发，最高相似度 0.683 离 0.85 还差得远。这与 atommem 在同一嵌入模型下的观察方向一致：
2048 维 embedding-3 的相似度分布整体低于原生的小模型尺度，导致按小模型调出来的阈值在这里偏向「放行」。
含义是去重机制在本臂实质上处于近乎不工作的状态——这不是 bug，是换嵌入模型的已知代价，
但做机制归因时不能说「本臂做了去重」，只能说「去重通道存在且从未触发」。
若后续发现记忆库里有明显重复条目，先查这一项。

### 4.2 这条臂的证据层是非确定的，而且抖动比其他臂都大

两次独立实测（各自 top_k=20，同一题连跑 3 次）：

| 观测 | 第一次（修审查问题前） | 第二次 | 第三次（最终配置） |
|---|---|---|---|
| 重构层拒绝率 | 70.15%（67 评估 / 47 拒绝） | 80.0%（60 / 48） | 74.24%（66 / 49） |
| 同题 3 次返回条数 | 2 / 2 / 2 | 1 / 1 / 1 | 2 / 2 / 2 |
| 三次结果的交集与并集 | 交集 1 、并集 4，不逐字相同 | 交集 1、并集 1，逐字相同 | 交集 2、并集 2，逐字相同 |
| 每题实际交付条数 | 召回 10 交付 2-6 | 召回 8 交付 1-3 | 召回 9 交付 1-4 |

> [!important] 上面三次都是小记忆库（16-20 条）下的观测，全量库下拒绝率明显下降（2026-09-12 首跑开跑后补记）
> 首跑（记忆库 305 条，即 3 个对话全部灌完）开跑后的前 49 题实测：
> 累计评估 980 条、拒绝 510 条，拒绝率 52.0%；每题实际交付证据最少 1 条、中位 9 条、最多 19 条。
>
> 趋势合理：库小时 top-20 里大量是不相关的近邻，自然被判「不适用」；库大了召回质量上升，接受率随之上升。
> 因此不要把小样本的 70-80% 当成本臂的固有拒绝率；证据体量仍然系统性低于其他臂
> （中位 9 条对 top_k=20，约四成卡），但没有小样本预测的那么极端。最终数字以跑完的全量统计为准。

两次的差异本身就是这条臂的性质：小库下拒绝率在 70-80% 区间浮动，跨轮次结果有时完全稳定、有时只有四分之一重合。
蒸馏层同样非确定（同一个 session 三次分别蒸馏出 5/5/8、5/5/7、5/3/8 条）。
两次观测都是小样本，不能当作全量拒绝率的估计值，只能说明量级与波动方向。

这件事对实验设计有三个直接后果，开跑前必须先接受：

1. 本臂交给答题模型的证据体量会系统性低于其他臂（其他臂稳定给满 top_k，本臂约给三成）。
   跨臂比较时，token 效率维度对本臂有利，绝对分数维度对本臂不利，两者要一起看。
2. 跨轮次方差里同时含重构噪声与答题噪声，且重构噪声占大头。atommem 已经是唯一检索层非确定的臂
   （逐字相同率 42.2%），本臂比它更不稳定。不能套用「检索确定 → 方差只含答题噪声」那套推论。
3. 三轮取平均是全臂统一配置，不为本臂单独加轮次；但解读本臂的方差时要标注它的方差来源与别人不同。

拒绝率 70% 本身是机制的真实表现，不是故障：论文把拒绝率当作核心观测指标，专门画了拒绝与接受的曲线。
需要注意的是，论文的拒绝率是在 agent 环境里、经过 GRPO 训练之后测得的，本臂是未经训练的通用模型
在会话问答上的表现，两个数字不可直接比较。

### 4.3 中文语料适用性：先解决语言问题再用

上游两层提示词全英文，论文明确要求英文输出并对非拉丁字符扣分。实测中文输入会被改写成英文，
且蒸馏层不稳定（三次里两中一英）。LoCoMo 是英文语料，本轮不受影响；但若将来要用自家中文语料
跑这条臂，必须先决定怎么处理这个冲突——照搬上游设计会得到中英混杂的记忆库，
而改成跟随输入语言则属于修改论文设计，需要单独立项并声明。

### 4.4 成本与时长（小样本实测，未做全量外推）

35 turns 实测：80 次 LLM 调用、19181 内部模型 token、ingest 约 7 秒/session。
其中蒸馏只占约 4.2k token（每个 session 一次调用），其余约 15k 都花在重构上——
本臂的成本大头在检索侧而不是构建侧，与 mem0、atommem 这类构建期重的臂正好相反。

重构调用量按「题数 × 轮次 × top_k」线性增长。LoCoMo 全量 1986 题、三轮、top_k=20 约为
5958 次检索、近 12 万次重构调用，这是本臂跑分时间的决定项。

> [!warning] 并发建模的更正（原文写错，由对抗审查指出）
> 此前写的「内部并发 4 × 评测并发 16 = 瞬时 64 路」是错的。评测循环的 Phase A（灌入与逐题检索）
> 是串行的，16 路并发只发生在不调用本臂的 Phase B（答题与判分），两者不相乘
> （`bench/runner.py:8-11` 的阶段说明与 `:243-254` 的逐题 `await` 可证）。
> 因此本臂的内部并发度就是服务端瞬时压力的上限，也直接决定 Phase A 的总时长。

并发取值的实测依据（2026-09-12，当时账户有其他会话共享配额）：

| 并发度 | 结果 |
|---|---|
| 4 | 无限流；但按此估算 Phase A 约需二十小时量级 |
| 12 | 撞账户限流，3 次调用失败，端到端验证被中断 |
| 8（当前默认） | 退避触发 0 次、失败 0 次，7/7 全过 |

遇到大量退避时降这个值，不要去降评测并发（降它不影响本臂）；跑完看 `stats().retry_count` 判断并发是否偷高。
检索侧单次调用的超时是 300 秒，8 路加三级退避理论上可能逼近它（最坏情况累计等待约 14 秒/条 × 批次），
全量跑前先小范围试一段确认。

以上除并发对照外，均按小样本推算，未经全量验证。
