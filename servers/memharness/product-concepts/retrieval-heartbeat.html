MemHarness 产品形态 ③ · 检索心跳

MemHarness 不是每一步都去查记忆库——agent 自己判断"这一步要不要查"，而且论文把检索次数 约束在每个 episode 1 到 5 次这个区间里，作为格式奖励的一部分。这个形态把一整个 episode 的执行过程画成一条心电图：大部分时候是平稳的"直接动作"，检索发生时是一次尖峰， 尖峰的疏密直接反映 agent 对自己经验库的依赖程度。

⚠️ 下面两条 episode 轨迹（ALFWorld / WebShop）、每一步的检索决策、 格式奖励提示，都是依据机制画像构造的示意数据，用于演示"自主决定检索时机 + 预算约束" 这条机制如何呈现，不是真实模型跑出来的日志。

为什么这个形态配 MemHarness

这批系统里，"什么时候查记忆"通常是被动的——固定每步查，或者按相似度阈值查。MemHarness 把这个 决策权交给 agent 自己（§3.2 Step 1："the agent decides whether to query"），而且这个决策本身 被纳入训练目标（检索频率是格式奖励的一项）。这意味着"检索的节奏"本身就是一个有信息量的信号—— 一个 agent 如果检索过密，可能说明它对当前任务不熟悉、缺乏自信；查得过疏或完全不查， 可能说明它在完全依赖参数化能力硬扛。心电图这个视觉隐喻直接对应"这是一个由 agent 自主控制节奏的过程"， 不是外部调度器按固定间隔触发的。

把预算（1-5 次/episode）做成可视化的"插槽"，是因为这个约束在论文里是训练信号的一部分而非 检索机制本身的硬限制（paper-architecture.md §5 明确指出这个数字只出现在格式奖励段落， 检索机制描述本身没提频率上下限）——产品上正适合做成一个"参考区间"提示，而不是强制拦截， 与论文的实际设计保持一致。

ALFWorld 和 WebShop 都是"同类任务反复做、经验会过时"的场景，这正是心电图节奏最有意义的场合： 同一个 agent 在跑第 1 次和跑第 100 次同类任务时，检索心跳的疏密理应不同——早期该多查， 经验积累后该少查——这条曲线的变化趋势本身可以是一个训练进度/记忆库成熟度的可读信号。

要诚实的一点：论文自己在"检索触发方式"上有内部张力——正文说"agent 自己决定"， 附录另一处又写"每步都检索"（paper-architecture.md §3 已指出这处矛盾未被论文调和）。 这个形态默认呈现的是训练脚本实际生效的 agentic 模式（论文两个训练脚本都显式启用）， 但如果部署方式切回 fixed 模式，"心跳"这个隐喻就不成立了——那时每一步都是尖峰， 图表退化成一条平的直线，这个形态需要显式声明自己依赖 agentic 检索模式这个前提。
