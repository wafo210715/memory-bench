# MemOS Paper ↔ Code 对照

> [!note] 口径
> paper = arXiv:2507.03724v4（Li et al.，首发 2025-07，v4 标注 2025-12-03，txt:1），评测用的是论文自称的 MemOS-1031
> code = MemOS repo @ `8553242`（2026-08-18，`__version__ = "2.0.30"`），实机配置以 `MemOS/.env` 为准
> 本仓库臂 = `servers/memos/server.py`（192 行纯 REST 转发，记忆逻辑全在上游容器内）
> 事实依据以同目录 `verification.md` 为准。论文与代码快照相隔约九到十三个月。
> 空格 = 该阶段在这一侧不存在。「默认死」= 代码完整但默认不可达，非损坏、非缺凭证。

> B8 空是三边一致的：论文全文没有迭代检索、失败重试或反馈式扩展（multi-hop 只是评测任务类别，不是机制）；代码是一次请求一次响应；臂只做一次调用。

## 三点最大区别

### 1. 三态记忆只剩一态，而系统提示词还在承诺另外两态

论文的核心主张是明文、激活、参数三类记忆统一封装调度并可跨形态迁移；代码的产品路径把激活和参数两个槽位直接写成空（`component_init.py:245-249`）。
明文转 KV 的函数是写好了的（`activation/kv.py:130`），所以这是默认死不是没实现；参数方向则连转换入口都没有，`parametric/lora.py` 只剩容器类。

这条属于「论文承诺在产品路径上不可达」，但不宜判成论文说谎：论文自己的 KV 加速实验（Table 8）也明说前提是「记忆已经预处理并缓存在 GPU 上」，那套由调度器自动识别高频稳定条目再转换的机制，论文里同样只是定性描述。

真正该修的是脱节的那一半：产品系统提示词至今写着 MemCube、MemScheduler、MemLifecycle、MemGovernance 四个模块名和生成→激活→合并→归档→冻结五态生命周期（`templates/mos_prompts.py:110,112,217,222`），而这些类在代码里全仓库搜不到定义，实际状态字段只有激活、消解中、已归档、已删除四个（`item.py:109`）。

### 2. 三层结构从未建立，检索侧因此一路退化

这不是四个并列缺陷，是一条因果链：

写入时记忆类型被硬编码成 fact（`simple_struct.py:229`），topic 和 concept 两层节点从未被创建，语义边也没建（A4）
→ 图遍历没有可走的结构，检索器名义上做图查找加向量合并，实际只剩向量（B3，`recall.py:81-98`）
→ 重排器的层级权重恒取默认值 1.0，因为它去 background 字段找层级名，那里存的却是 LLM 摘要（B4，`cosine_local.py:56,88-90`）
→ 论文那套「查什么、去哪查、按什么顺序查」的任务分解无从谈起，快速模式下查询解析退化成恒等映射（B5，`task_goal_parser.py:73-81`）

四层里只有第一层是主动选择（先做扁平事实），后三层是被动后果。判定成「能力损失」还是「尚未实现」取决于第一层：`_ensure_structure_path` 这个建层级路径的函数在生产代码里没有任何调用点，只有测试在调（`verification.md` C84），说明它是留着没接上，不是被摘掉的。

### 3. 检索的并行与截断结构是纯加法，论文一笔没画

论文只画了一次检索接一次调度的线性流程；代码在这一段长出了论文没有的两层结构。

| 层 | 代码实际做法 | 论文对应 |
|---|---|---|
| 召回并行 | 六条路径并发提交，线程池上限 5；长期记忆那条内部再开三线程 | 无，论文是单次检索 |
| 路径内重排 | 每条路径各自先排一次，之后才合并 | 无，论文的排序是全局一次 |
| 合并 | 六路结果简单拼接，无倒数排名融合、无加权 | 论文说符号过滤与语义排序可复合 |
| 截断 | 文本去重 → 按类型分桶取前 k → 相关度阈值 0.45 → 三倍候选池里做最大边际相关 | 无，论文只提调度器选注入策略 |

记忆类型的分类层级也是纯加法：论文的三分类是系统级的明文、激活、参数，代码的十个取值（工作、长期、用户、外部、工具 schema、工具轨迹、原始文件、技能、偏好、上下文，`item.py:178-189`）全部是明文内部的子分类，论文完全没写到这一层。

> [!warning] 这些数字不能直接用来读本仓库的 memos 臂
> 三点原因：被测版本是 MemOS-1031，本仓库跑的是 2026-08-18 的 v2.0.30；论文给每个方法都调到了各自最优配置，本仓库一律用上游默认配置加统一 embedding 口径；论文的 LoCoMo 分数是 MemOS 端到端出答案，本仓库只把它当检索服务、答题模型在进程外。
> Table 8 那一栏还有一层：它测的是「记忆已经预处理并缓存在 GPU 上」这个前提下的收益，属于实验装置而不是运行时会自动发生的机制——对应代码里 A6 默认死。

## 附：两条推导

1. 0.45 这个阈值在本仓库臂上的后果，比在论文语境里严重得多。上游把它设成默认值时，配套的是自家最优配置下的分数分布；本仓库用统一 embedding 口径跑，1986 题里 78 题所有候选都低于阈值、直接返回零证据，621 题不足五条（`verification.md` C102 已独立复算）。零证据的题必然答错，出分时应当单列，否则会把检索阈值问题读成记忆能力问题。
2. 时间类题目在本臂上还额外少一个锚点。信封里的时间戳本意是取对话发生时间，但那个字段只存在于每条记忆的来源子结构里、从未提升到元数据顶层，取值恒为空并回落到入库墙钟（`item.py:40`、`server.py:143`）。而入库墙钟对本臂来说是灌库那一刻的时间，与对话真实时序无关——也就是说时序推理类题目拿到的时间信息实际上是噪声，不是弱信号。写入侧同样没往消息里塞对话时间（`server.py:77`），所以这条链两端都断着。
