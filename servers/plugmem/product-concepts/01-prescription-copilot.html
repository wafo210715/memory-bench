处方 Copilot —— 复用「上次怎么做成的」

一个挂在执行型 agent 旁边的悬浮面板：agent 即将开始一类重复性操作时，面板从 PlugMem 的程序图里调出 最匹配的「意图 + 处方」，交给人确认或直接采纳，而不是让 agent 从零摸索或完全自主决定。 面板的角色是复用，不是聊天——处方本身就是一段可执行步骤。

网店后台运营 Agent　·　任务：下架断货商品并归档 SKU

意图：下架高退货率商品

这条处方来自另一类任务，与当前查询「清理无库存 SKU」相似度较低。默认配置下程序记忆检索是 「最匹配的 1 个意图 → 该意图下最匹配的 1 条处方」（top-1 → top-1），不会把它带出来； 这里手动放开候选数量，模拟「如果产品要支持多候选比较，需要把检索的 k 值主动放开」之后的样子。

为什么这个形态配 PlugMem

机制依据：程序图把「一类任务过去是怎么做成的」结构化成 intent + prescription 对—— 轨迹先按相邻子目标相似度切段，每段抽出一条处方，并留有 provenance 边指回全部源情景（可展开核实）。 这不是把旧对话重新搬出来读一遍，而是把它压成一段可直接执行的操作建议，所以配「卡片 + 应用按钮」 比配「搜索结果列表」更贴近它的性质。

插件式边界：这个面板可以挂在任何执行型 agent 旁——任务开始前查一次程序图， 任务结束后把新轨迹写回去，不需要改 agent 自身的决策逻辑。论文把「不改 base agent、挂上去就能用」 当作核心定位，这正是它区别于「重新训练一个更懂任务的 agent」的地方。

适用场景：对应 WebArena 一类站点任务（Shopping / GitLab / Multi-site）。 这类任务的核心特征是「同类操作会被反复执行」，正是「意图 + 处方」复用能派上用场的地方； 具体成功率数字在复核材料里未能可靠转写，这里不引用不确定的百分比。

诚实的局限，共四点：

① 上面「质量分：暂不可用」不是 UI 占位——论文里独立评委打分的调用点在代码中确实是零， 处方之间目前没有可信的质量排序信号，产品要用这个分做决策，得先把评委补回去。

② 默认检索路径只回 1 个意图下的 1 条处方（程序模式意图阈值 0.1、处方 top-k 默认为 1）。 面板上「查看更多候选」这类多选体验，需要主动放开默认的 k 值，不是开箱即有。

③ 意图去重在代码里从「embedding 余弦相似」退化成「字符串完全匹配」， 同一件事换个说法就会各建一个新意图节点。长期使用后程序图容易堆积措辞不同、语义重复的意图， 稀释掉真正该被复用的那条处方——这个面板如果长期上线，需要自己补一层归并逻辑。

④「标记无效」按钮目前更多是产品愿望：从现有架构描述看，记忆图的更新路径是 LLM 自动检测语义矛盾或按命令行开关合并重复节点，没有看到「消费一次人工反馈点击」的写入接口—— 真要支持人工纠偏，需要单独设计一条写入通道。
