## 一、分级 Findings

### CRITICAL

#### C1 · 第二说话人的全部话语从不进入命题抽取

语义图只覆盖约一半对话，且覆盖的是哪一半逐段随机。

位置：

| 侧 | 位置 | 内容 |
| --- | --- | --- |
| 本臂 | `server.py:394-408` | `_sides`：第一位说话人 → observation 侧，其余 → action 侧 |
| 本臂 | `server.py:62-71` | 口径 6 注释 |
| 上游 | `plugmem/inference/structuring.py:73` | `get_semantic` 的 `variables = {"observation": step["observation"]}`，只读 observation |
| 上游 | `plugmem/prompts/structuring.py:161` | GetSemanticPrompt 的 `{observation}` 是唯一文档槽位 |

问题：PlugMem 的语义命题（semantic proposition，即「事实句 + 标签」）只从每步的 observation 抽取；action 字段进 episodic 节点和状态摘要，但永远不被 `get_semantic` 看到。上游 LME 脚本这样做没问题（assistant 话语不是提问对象），LoCoMo 是双人对话，两人都是提问对象。

用 `loaders/locomo.py` 全量数据加本文件的 `_sides` / `_pair_turns` 实测：

| 统计口径 | 结果 |
| --- | --- |
| 全部 turn | 5882 |
| 落在 action 侧的 turn | 2871，占 48.8%（41.2 万字符） |
| gold evidence 的 turn | 2806 |
| gold evidence 中落在 action 侧 | 1355，占 48.3% |
| 开场说话人分布（示例 conv） | 19 段里 Caroline 开场 15 段、Melanie 4 段 |

也就是说被抽取的那个人逐段翻转。

后果：情景模式靠命题投票定位会话（`_recall_episodic`），命题层缺了一半事实，投票信号系统性偏向「开场者说的事」；语义模式则直接检索不到那一半。这不是论文机制，是适配层产物，`arm-reproduction.md` §2.1 未声明。跑出来的分数会被解读成「PlugMem 三图协同的召回能力」，实际是「半份语料上的召回」。

修复建议（三选一，都不改上游代码）：

| 方案 | 做法 | 成本 |
| --- | --- | --- |
| a（推荐） | `_build_memory` 在 `mem.close()` 之后，对每步 `step["action"]` 再调一次 `get_semantic(llm, {"observation": step["action"]}, j, i, time)`，把结果连同 embedding 追加到 `mem.memory["semantic"]` / `memory_embedding["semantic"]`（trajectory_num / turn_num 同该步），turn_range 逻辑不用动 | 约 +1 次调用/步（约 +25%） |
| b | 每个说话人块都当 observation（step =（块 i, 占位动作）） | 步数翻倍，成本约 ×2 |
| c | observation_i = obs 块 + act 块拼接，action 用占位 | 步数不变，但子目标/奖励标注语义更扭曲 |

必须重灌，正在跑的 ingest 产出的图不可用。

### MAJOR

#### M1 · 语义模式下标签路由通道被「稠密池扩到 top_k」完全抵消

实际等价于纯稠密检索。

位置：`server.py:548-567`（`_recall_semantic`）、`server.py:52-56`（口径 5）；上游 `memory_graph.py:686-699`（稠密池写死 5）、`:714-741`（标签投票）、`:759-787`（纯余弦排序取 k）。

问题：最终排序是纯余弦（上游 importance / recency 恒 0，`value_functions.py:70-88`），标签通道在上游的唯一作用是扩候选池（稠密 5 加标签路由的节点，再取前 10）。本臂先算全库稠密 top_k，再并上路由结果、按余弦重排取 top_k。任何路由进来的节点，余弦若高于稠密第 k 名就已在稠密 top_k 里，否则排不进。除并列外，结果恒等于稠密 top_k。论文 B3「高层节点路由激活低层节点」在本臂语义模式下是空操作，但口径 5 写的是「标签路由 ∪ 稠密 top_k 重排」。

修复建议：稠密池保持上游 5（或 top_k 的固定比例），把标签路由的候选与稠密候选合并后再按余弦取 top_k；或在口径里明确写「语义模式 = 命题层稠密检索，标签通道无效」。只改 retrieve，不需要重灌。

#### M2 · 多跳控制器只在语义模式真正生效

情景 / 程序模式的第二跳退化为重复查询。

位置：`server.py:665-676`（`_hop_control` 的 id 命名空间：episodic_id / semantic_id / procedural_id 三类 int 混用）、`:846-847`（`focus` 只按 `semantic_id` / `procedural_id` 匹配，EpisodicNode 用 `__slots__` 无 `semantic_id`，`getattr` 返回 None，`None in picked` 恒 False）、`:829`（程序模式第二跳仍用 `next_subgoal`，而 `:849` 丢弃了新 subgoal）。

问题：情景模式（`arm-reproduction.md` §5.3 实测 LoCoMo 上压倒性被选中）下 `focus` 恒空，`hop_query = query + "\n"`，第二跳召回与第一跳相同；程序模式第二跳查询字面相同。第二跳只剩成本（1 次 hop judge、1 次 get_plan、1 次 embedding），没有效果。id 冲突还会让 `picked` 里本意指情景节点的 id 误匹配到同号命题。口径 3 声称「按论文 Listing 10 实现」，在主路径上不成立。

修复建议：id 加类型前缀（`e:3` / `s:3` / `p:3`）；情景模式的 focus 用 `episodic_id`，把命中情景节点的文本拼进下一跳；程序模式让第二跳使用新 subgoal。

#### M3 · 意图语义判重触发的是「X 与 X 合并」

论文语义未复原，上游文本 / 向量脱节缺陷被放大。

位置：`server.py:500-530`（`item["subgoal"] = best_str`）；上游 `memory_graph.py:515-524`（`subgoal2node.get(subgoal_str)` 命中后 `get_new_subgoal(subgoal_node.get_subgoal(), subgoal_str)` → 刷新 embedding）、`retrieving.py:123-130`（返回原始整段回复）。

问题：新意图字符串在入图前已被改写成已有节点的原串，上游合并 LLM 看到的两个 goal 完全相同，新意图的措辞在到达 LLM 之前就被丢弃。论文的「合并改写」退化成「让 LLM 复述一遍旧串」，还把节点 embedding 换成这段复述文本（含 `Merged goal:` 前缀）的向量。差异 #10（向量刷了文本没写回）在上游只有字面完全重复时触发，本臂每次语义命中都触发（`intent_merged` 计数就是触发次数）。`arm-reproduction.md:45` 写的「未被放大」判断不成立。每次命中额外浪费 1 次 LLM 调用。

修复建议：在 server 进程内 monkeypatch `plugmem.core.memory_graph.get_new_subgoal`（不改上游仓库文件），让它接收（旧串, 原新串）并返回合并结果；或在 `_merge_intents_semantically` 里先自己调 `get_new_subgoal(old, new)`，把合并串写回 `item["subgoal"]` 与已有节点的 `subgoal` / `subgoal2node` 键，再让上游走新建分支。

#### M4 · 末尾占位动作步污染程序记忆并制造伪切段

文档少算成本。

位置：`server.py:453-459`；上游 `memory.py:59-102`（append 对占位步同样做 3 次标注并做切段判断）、`memory.py:123`（get_procedural 吃到 `-Action: Agent Say: (no reply)`）。

问题：272 段里 140 段（51%）会补占位步。占位步的 subgoal 是对「不回复」的解释，与前一步相似度大概率低于 0.75（本臂切段率已 72%），于是多出一个只含占位步的轨迹段，产生一条关于「不回复」的处方和一次质量分打分，进入程序图。命题层不受影响（`get_semantic` 只读 observation），但程序图多了垃圾节点，程序模式被选中时可能被返回。`arm-reproduction.md:60` 写「多三次标注调用」，实际是 3 次标注、1 次命题抽取、大概率 1 次处方、1 次质量分，约 6 次/段。

修复建议：不走 `mem.append`，而是在 `close()` 前直接向 `mem.trajectory` 追加一个合成 step dict（observation = 最后 obs 块，action = 空串，subgoal = 上一步 subgoal 以免切段，state = 当前 state，reward = 空串），零 LLM 调用、不产伪段；EpisodicNode 对空 action 已自然跳过（`graph_node.py:45-48`）。

#### M5 · 情景模式预算修法：满票会话的命题被整体移出命题侧

情景侧超出半预算的直接证据随之丢失。

位置：`server.py:611-641`。

问题：`prop_items` 排除了所有满票会话的命题（`:630-631`），它们只以情景节点的身份进 `episodic_items`；`ep_take = min(len, ep_budget)` 后被截掉的情景节点（含被命题直接投中的高分节点）没有回落到命题侧，而命题侧却在用非满票会话里相关度更低的命题填满。当满票会话的直接命中节点总数大于 top_k/2（30 票池集中在两三段会话时很常见）就会发生「高分证据被丢、低分证据入选」。另外 `:624` 的折价兜底节点先于全局排序占用半预算，无论其分数是否低于命题侧候选。

修复建议：被 `ep_take` 截掉的情景节点，把投中它的命题回填到 `prop_items` 参与命题侧排序；折价兜底节点参与全局排序后再截。

## 三、修复优先级速查

> [!warning] 必须在重灌前修
> C1：action 侧话语进不了命题抽取。这是唯一一条会让已灌入的图整体作废的缺陷。

> [!tip] 可与重灌并行，但应在出分前修完
> M1（语义模式标签通道空操作）、M2（多跳在主路径失效）、M5（情景预算截断丢高分证据）。
> 三条都只改 retrieve，不需要再次重灌，但不修会让机制归因失真。

> [!note] 可排期
> M3、M4 影响成本与程序图质量，MINOR 十条多数是口径声明与统计可解释性问题。
> m7（token 三桶重复计数）在写跨臂成本表之前必须先明确口径。
